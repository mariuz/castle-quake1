# Castle Quake: How Each Roadmap Item Was Done

The implementation notes of the finished items of [ROADMAP.md](ROADMAP.md), phase by phase: what was built, where it lives in the code and how it is tested. For the current structure of the code see [ARCHITECTURE.md](ARCHITECTURE.md).

## Phase 4: Progression, UI, & Game Flow

**Episode Portals & Hub Flow.** `trigger_setskill` sets the skill used to spawn the next maps (`SPAWNFLAG_NOT_EASY/MEDIUM/HARD` for entities and brush models; nightmare limits monster pain), `trigger_changelevel` keeps the inventory like `SetChangeParms` (no keys or powerups, health 50..100) and a death restarts the level with the inventory it was entered with. Runes (`item_sigil`) set the server flags: back on the start map the player spawns at `info_player_start2` with a new inventory, `func_episodegate` closes completed episodes and `func_bossgate` opens with all four runes. `trigger_multiple` / `trigger_once` now honour `wait`, one-way angles and centerprint their messages. Portals to episodes missing from the paks say so. Single Player offers the id1 hub (from `quake1_demo.pak` or `id1/pak0.pak`, even though the bundled LibreQuake pak replaces `start.bsp`) and the LibreQuake hub; `-game quake` does the same from the command line.

**Intermission Screen.** leaving a level through a `trigger_changelevel` without `NO_INTERMISSION` freezes the player and looks from a random `info_intermission` spot (`mangle`) to the intermission music, while the HUD draws `Sbar_IntermissionOverlay` from the PAK pictures (new `QuakePics` unit for `gfx/*.lmp` and `gfx.wad` qpics) under the level title. Time, secrets and kills count up one after another with ticks. After 5 seconds fire, jump or use loads the next map. `trigger_secret` now counts secret areas ("You found a secret area!").

## Phase 5: Advanced & Modding Features

**Software Lightmap Rendering Option.** `QuakeGeometry` packs every lightstyle layer of each face (up to 4, `TBSPFace.Styles`) into its own atlas and renders the world with an unlit material plus a GLSL `Effect` that sums the layers scaled by the current lightstyle values (flickering torches, pulsing lights on the walls, like `R_BuildLightMap`) and adds the dynamic lights of muzzle flashes and explosions (`R_AddDynamicLights`, `TQuakeLighting.AddDLight`), with Quake's x2 overbright. The alternative "Dynamic PBR" mode (Options menu, console `lightmaps 0`, demo action `B:0`) lights physical materials with the map's point lights (now attenuated) and shadow maps instead. Textures are kept in sRGB (no gamma correction).

**Savegames and Demo Recording in QuakeC Mode.** `TQuakeProgs.SaveState` / `LoadState` dump and restore the VM (globals, the used edicts with their free flags, engine strings, precache lists; the progs crc must match), `TQuakeQcGame.SaveGame` / `LoadGame` add the map, skill, time, statics, lightstyles and view angles (`castle-config:/qc_save_<slot>.sav`), and `TViewQc` rebuilds the level around the restored game (`SetupLevel`, which also re-applies the lightstyles the progs set while spawning). Demo recording uses `TQuakeDemoWriter` like the native game: client data from the player's fields, every visible edict per frame, sounds, prints, centerprints, temp entities, damage, kills, secrets and the intermission. Verified on e1m1: save, turn, load (165 edicts back, view restored) and a recorded demo that plays in the demo view.

**Projectiles and Gibs in Savegames.** `SaveGame` writes every projectile (kind, origin, velocity, life, resting, spin, homing timer, the monster that fired it) and gib (model, origin, velocity, angular velocity, angles, life, resting); `LoadGame` recreates them after the monsters, so a grenade fuse or a rocket in the air continues from the save.

**Turbulent Liquid Surfaces.** every liquid batch gets a GLSL `Effect` (`LiquidFragmentShader`, `PLUG_texture_coord_shift`) that offsets each texture coordinate by 8 texels of a 64 texel texture with turbsin (`uv + 0.125 * sin(uv.yx * 8 + time)`), `liquid_time` advanced by `TQuakeGeometry.Update` with a 2 pi period; the surfaces stay translucent. In both world lighting modes.

## Phase 6: Inspectable in Castle Game Engine

**Named Components and Owned Hierarchy.** `ComponentName` (`QuakePak`) makes identifier names with a running number per base, reset on every level (`world`, `func_door_7`, `monster_army_3`, `pickup_healthnormal_2`, `projectile_rocket_1`, `gib_gib1_4`, `light_torch_small_walltorch_9`, `ambient_comp1_2`, `edict_12` / `entity_12` in the QuakeC and demo views, `view_weapon`, `camera`, `sound_pool_N`); the scenes under them are `<name>_scene`. The engine's inspector is enabled in every build (F8, or three fingers), and the demo action `I` logs the same tree (`Scene tree: N transforms`). Found and fixed on the way: a level's point lights and the muzzle light were never freed on a map change.

**Entities as Behaviors.** `QuakeBehaviors` attaches `TQuakeMonsterBehavior` (class, health, state, yaw, targets, alerted, ambush, enemy), `TQuakePickupBehavior` (kind, collected, respawn, message, target, model), `TQuakeSubmodelBehavior` (class, state, open, speed, wait, targets, key needed, spawnflags, model index) and `TQuakeTriggerBehavior` (class, targets, map, message, touchable, removed, wait, spawnflags, bounds) to every entity when a level spawns; triggers, which have no model, get an empty named transform at the centre of their box under `triggers`. Writable properties act on the game (health, yaw, collected hides the item, open triggers a door, touchable / removed / wait on triggers). The demo action `I` lists the behaviors under their transforms (`@monster_behavior_3: TQuakeMonsterBehavior`); e1m1 shows 23 monster, 24 pickup, 55 submodel and 25 trigger behaviors.

**Map Export to X3D / glTF.** `TQuakeGeometry.ExportMap` builds the world and every brush model again into one scene graph, each a named `Transform` (`world`, `func_door_1`, `func_button_4`...), adds the light entities as `PointLight`s with the game's colors, radii and attenuation, writes the textures as PNG files into a `textures` folder next to the file and saves with the engine's `SaveNode` (X3D, or glTF by the extension). The materials are the physical ones lit by the exported lights: the lightmap atlases and their shader belong to this renderer (and would be megabytes of pixels as text). e1m1 gives a 1.3 MB X3D with 58 transforms, 126 shapes, 198 lights and 68 textures that opens in the CGE editor and view3dscene. The engine's glTF writer does not keep the texture references, so the glTF has the geometry, materials and lights only.

**Debug Overlays and Console Commands.** `QuakeDebug` draws an unlit line-set overlay (`debug_overlay` transform) rebuilt every frame by `TQuakeWorld.UpdateDebugOverlay`: trigger boxes (green, gray once fired), monster boxes (yellow, red when alerted) with a sight line to the player's eye, mover bounds (cyan), the player's BSP leaf (magenta), the player box and projectile markers. Console `debug <all|off|triggers|monsters|movers|leaf>` and demo action `D:modes` toggle it, console `fps` shows the frame timing on the HUD, and `E` in QuakeC mode logs the edicts in use (classname, origin, health).

**Split `quakeworld.pas`.** `quakeworld.pas` keeps the `TQuakeWorld` declaration (290 lines) and includes `code/world/quakeworld_{game,map,player,weapons,monsters,movers,pickups,save,record,debug}.inc`, each a self-described subsystem of 70 to 850 lines. They stay include files of the one class (CGE's own `castletransform_*.inc` style) because every subsystem reads the shared private state; turning them into units would need the state exposed through a world interface, which is left for when a subsystem gets its own unit tests.

## Phase 7: Beyond the Shareware

**Multiplayer Prediction and Connectivity.** inputs carry a sequence number and their duration; the server runs each player for exactly its inputs (`TQuakeQcGame.RunClientInput`, like `SV_RunCmd` of QuakeWorld) and every frame packet names the last input applied. `TViewDemo` keeps a `TQuakePlayerPhysics` of its own and the inputs not yet acknowledged: on every server frame it resets to the server's origin and velocity and replays them, so the camera follows the local player without the round trip (`-nopredict` turns it off; the headless screenshots log the prediction error). UDP hole punching through a rendezvous service built into the executable: `-rendezvous` runs it, `-host <map> -register name@rendezvous[:port]` keeps a host registered there, `-connect name@rendezvous[:port]` looks the name up, gets the host's public address and the host punches a hole towards the client. The WebSocket relay for the web build is not done: the web build has no sockets at all.

**Mission Packs and the `-game` Switch in QuakeC Mode.** `-game <dir>` (a name or a path) loads `<dir>/pak0..pak9.pak` from the working directory, next to the executable, the data or the config directory on top of id1, so the pack's `progs.dat`, maps, models, sounds and `gfx` pictures replace the originals in every mode: `-game hipnotic -qc start` runs Scourge of Armagon with its QuakeC. The QuakeC view reads rogue's `items2` into the high item bits (like `SV_WriteClientdataToMessage`) and in hipnotic the keys 9 and 0 send the laser cannon and Mjolnir impulses (225, 226). Verified with a test directory whose pak overrides `start.bsp` and `progs.dat`; the packs themselves are not bundled.

**Full Registered Content.** the intermission has the stages of `ExitIntermission` (client.qc): the tallies, then the episode text after e1m7 / e2m6 / e3m7 / e4m7 (the shareware variant of the first one when episode 2 is not installed), then the all-four-runes text, each dismissed with a button, typed out over `gfx/finale.lmp` at 8 characters a second (`TQuakeHud.StartFinale`). Teleporting telefrags whatever stands at the destination; `misc_teleporttrain` (the spiked ball of `end.bsp`) runs along its `path_corner`s and is a valid teleporter destination, and telefragging `monster_oldone` plays `finale_1` .. `finale_4` of oldone.qc: the intermission view, a teleport splash inside her, her death cry with the flickering lightstyle, the pop into forty gibs and the ending text; a button then starts a fresh game in the hub. Verified headless on e1m7 (rune, exit, tallies, text, the hub with rune 1) and on a test `end.bsp` built from E1M1 with Shub, the train and a teleporter (the registered assets are not bundled).

**Audio Polish.** `TQuakeSounds.PlayTrack` plays `data/music/trackNN.ogg` for the worldspawn `sounds` key of the map in every mode (track 2 when the file is missing), `svc_cdtrack` switches the track in the demo / network client and in QuakeC mode (the finale's track 3), and under water every OpenAL source gets an EFX low-pass filter (`SetUnderwater`, high-frequency gain 0.2; no-op without EFX or on the web).

**Rendering Polish.** a worldspawn `sky` key with `gfx/env/<name>{rt,bk,lf,ft,up,dn}.tga` in the paks renders the sky surfaces through a six face skybox shader (the face orientation of the original skybox code), else the scrolling two layer sky stays. World textures carry the fullbright palette entries (224..255) in their alpha channel and the lightmap shader keeps those texels at full color. `R_LavaSplash` is a particle effect (`SpawnLavaSplash`) played when Chthon rises, for `TE_LAVASPLASH` in demos, network play and QuakeC mode, and recorded in demos; slime has no effect of its own in Quake. Liquid surfaces are two sided with `r_wateralpha` 0.65 by default, from above and from inside, and the console `wateralpha <0..1>` changes it live. Verified headless with a test pak (a labeled skybox on E1M1), the E1M1 water from inside and Chthon's rise.

**Automated Test Coverage in CI.** `tests/quaketests.lpr` (its own `CastleEngineManifest.xml`, no window) runs against the bundled shareware pak: point contents and hull traces on E1M1, `anglemod` through the VM opcodes, the known E1M1 spawn counts (336 entities, 161 edicts, 23 monsters, 6 secrets) and 10 s of thinks, a VM `SaveState` / `LoadState` round trip compared edict by edict, `TQuakeSaveData` through a file, and a demo written by `TQuakeDemoWriter` read back by `TQuakeDemoReader` (level, models, prints, client data, entity states). The `test` job of the Build workflow builds and runs it and the release job depends on it.

**Input.** `GameInput` holds every action as a `TInputShortcut` (move, walk, jump, fire, use, the eight weapons, next / previous weapon, quick save / load, console, camera, shadows, screenshot) with the previous keys as defaults; the play, QuakeC and multiplayer views read them, and the Options > Controls menu rebinds any of them to the next key, mouse button or wheel direction pressed (`Reset to defaults` too), saved to `UserConfig` through their own `BindingList.SaveToConfig` and loaded at start. The gamepad (CGE's `CastleGameControllers`): the left stick moves, the right stick turns, A jumps, X uses, RB or the right trigger fires, the D-pad changes weapons (impulses 10 / 12 in QuakeC and multiplayer), and the D-pad, A and B walk the menus.

## Phase 8: Reach and Robustness

**Multiplayer in the Browser.** `QuakeWebSocketRelay` is a non-blocking TCP server (RFC 6455 handshake, unfragmented binary messages, ping / pong, close) giving every browser its own UDP socket towards the game server, so the server is unchanged; `-host <map> -websocket <port>` runs it next to a listen server, `-wsrelay host[:port]` alone. `QuakeWebSocketClient` is the web build's transport: a `WebSocket` created through Job.JS by a small JS factory (everything that can throw stays in JS try / catch, because WebAssembly cannot catch exceptions) and polled every frame; `TQuakeNetSocket.CreateWebSocket` puts it behind the same client code, and the page joins with `?connect=host[:port]` (TCP port 26001 by default, `wss://` from an https page). Verified with the web build in headless Chromium joining a native host through the relay (signon, frames, its shot reaching the server) and a Node WebSocket client through the standalone relay. No TLS in the relay: an https page needs a TLS proxy in front.

**Gamepad Testing and Tuning.** Options > Controls shows the connected pad (Enter looks again) and cycles look sensitivity (0.5x to 3x), dead zone (0.1 to 0.4) and inverted look, saved in the user config (`gamepad/*`). Without hardware the controller paths are tested through the engine's explicit controller backend: the demo script's `GL` / `GR` (sticks), `GT` (right trigger) and `GB` (buttons) drive a virtual pad in the play view, and the unit tests check the dead zone, the stick movement, the turn rate (80 deg in 0.5 s at sensitivity 1), sensitivity, inverted look, the 85 deg pitch limit and the saved settings. A headless E1M1 run changes weapons with the D-pad, fires with the bumper and the trigger, walks with the left stick and looks up with the right one. The button mapping on real pads is still unverified (next item).

**Gameplay Scenarios in CI.** `tests/scenarios.py` runs four scripted games and checks their logs: E1M1 (walking with the physics, the exit trigger, the intermission, a button loading E1M2), a save and load in a fight with two grunts (two shots fired, health below 100, the load restoring exactly the saved health, armor, shells, kills and monster count, the fight going on after the save), a host and a client (the client joins, completes the signon, its shot reaches the server, the prediction error stays under 32 units) and QuakeC mode (E1M1 spawned through `progs.dat`). Every screenshot's 3D view must not be black, and the stable ones are compared with `tests/reference/*.png` at 160x90 (mean absolute RGB difference at most 5 of 255: runs differ by less than 0.5, a wrong view or untextured walls by more than 9); a failure writes the actual, reference and difference images side by side. The `scenarios` job of the Build workflow runs it under Xvfb, uploads the screenshots and logs, and the release depends on it; `--update` rewrites the references.

**Rendering Performance on Large Maps.** the world is split along the BSP tree into clusters of at most 256 faces (146 on E1M1, 140 on lq_e0m2), each with its own texture batches; a cluster is drawn when a leaf listing its faces (marksurfaces) is in the PVS of the camera's leaf, recomputed only when the camera changes leaves (`TQuakeBsp.LeafPVS` decompresses the row). Maps are not vised through water, so with translucent liquids the leaves on both sides of every liquid surface add each other's PVS. Hidden shapes keep their collisions. Outside the map or without vis data everything is drawn; console `novis 1` and demo action `N:0` turn it off, `Z` logs frame times. Checked by screenshot pairs with culling on and off at 24 spots on each of E1M1, E1M3, E1M5 and lq_e0m2 (differences only from moving monsters) and a unit test of the PVS rows. Frame times under llvmpipe (software GL, 800x600): LibreQuake start 43.9 -> 22.9 ms, lq_e0m2 68.4 -> 46.9 ms, E1M1 start 63.4 -> 36.6 ms, E1M3 start about the same (16-18 ms). The registered maps are not in the container, so they are not measured.

## Phase 9: Modern Maps and Polish

**Entity PVS Culling.** every frame the world bounding box of each monster, item, missile, gib and brush entity scene is pushed down the BSP tree (`TQuakeGeometry.BoxVisible`, like `SV_FindTouchedLeafs`) and the scene is drawn only when a touched leaf is in the camera's PVS, in the play, QuakeC and demo views; a hidden MDL scene skips its pose updates, collisions are unchanged and pickups keep their own collected flag. Demo action `NC` renders one frame with culling on and off and logs the differing pixels: 0 in 184 views on E1M1, E1M3, E1M5, E1M7, start and lq_e0m2 (a deliberately broken check was caught), with a third to a half of the entities drawn. Frame times under llvmpipe at the map starts (everything drawn / world culling only / world and entities): lq_e0m2 65.1 / 46.9 / 21.5 ms, E1M1 64.0 / 36.6 / 25.7 ms, LibreQuake start 40.8 / 22.9 / 19.9 ms, E1M3 about 16 ms in all three (its hidden entities are already outside the view frustum).

**Lightmap Atlas Pages.** `TQuakeGeometry.AddFace` packs into the last page of a `TQuakeLightmapAtlasList` and opens a new page (same size, with its own 4x4 gray block) when a lightmap does not fit; batches are keyed by texture and page, and every page gets its own `TQuakeLightmapSet` (effect, layer textures, lightstyle and dynamic light uniforms). The log reports `Lightmaps of model N: P atlas page(s) of SxS, R rows used, F faces without room` (F only counts a face larger than a whole page). The bundled maps stay on one page (E1M1 uses 236 of 2048 rows, lq_e0m2 449), so `-lmatlas <size>` shrinks the pages for testing: E1M1 with 256, 128 and 64 texel pages spreads over 7, 25 and 91 pages with no face left fullbright and the same image as one page (at most 46 pixels differ, from an animated torch), in both world lighting modes. The `lightmap_pages` gameplay scenario renders E1M1 with 128 texel pages against the one-page reference.

**BSP2 and Extended Limits.** `TQuakeBsp.LoadFromStream` reads BSP29, `BSP2` and `2PSB` into the same wide records (32-bit node, leaf, face, edge, clipnode and marksurface indexes, float bounds); BSP29 children are unsigned like QuakeSpasm. With no BSP2 map in the bundled paks, `tests/bsp2convert.py` rewrites E1M1 in both formats: they load with the same 5516 faces, 146 PVS clusters and 1148 leaves, render the same start view (at most 42 pixels differ, from an animated torch) and walk the same route on their clipping hulls, which the new `bsp2` gameplay scenario checks in CI. Protocol 666: the demo reader (also the network client) reads FitzQuake's extension bits for entities, client data and sounds, `svc_spawnbaseline2`, `svc_spawnstatic2`, `svc_spawnstaticsound2`, `svc_skybox` and `svc_fog`; the demo writer and the network server write them for numbers above 255 and announce 666 for those levels (`-protocol 666` always), up to 2048 models and sounds and 8192 entities. A unit test round-trips models, frames, sounds, armor, cells and the weapon frame above 255 and a sound from entity 9000; a host forced to 666 plays with a client (signon, a shot reaching the server, prediction error at most 3.6), a 666 demo recorded on E1M1 plays back, and protocol 15 demos still play. Not done: coordinates stay 16-bit (RMQ's protocol 999 and maps beyond +-4096 units), and the fog and skybox messages are read but not shown yet (next item).

**Colored Light and Fog.** `TQuakeBsp.LoadLit` reads `maps/<name>.lit` (QLIT version 1, three bytes for each lightmap byte) from the paks, a `-game` directory's loose files or a `.pk3`; the lightmap atlas pages then hold RGB texels (`TQuakeLightmapAtlas` with `Rgb`) and the lightmap shader multiplies by an RGB light (`quake_lm_rgb`), lightstyles and dynamic lights unchanged. The worldspawn `fog` key (`density` or `density r g b`, FitzQuake's gray 0.3 default) becomes the viewport's `TCastleFog` in the play, QuakeC and demo views (`ApplyWorldFog`): FitzQuake's GL_EXP2 fog with density / 64 is approximated by the engine's exponential fog with the range that reaches one half at the same distance (`130.2 / density`); the console `fog <density> [r g b]` sets it for the level. The `litfog` gameplay scenario renders E1M1 with a `.lit` made of its own gray light (the same image as without it, difference 0.2), a red tinted `.lit` and a fog key, the last two against their own references; `tests/bsp2convert.py` gained `make_lit` and `set_worldspawn_key` for it.

**Video Options.** `GameVideo` keeps the field of view, gamma, view bob and the view weapon (`video/*` in the user config, the Options menu and the console `fov`, `gamma`, `cl_bob`, `r_drawviewmodel`). `fov` is the horizontal angle at 4:3 and becomes a vertical field of view (`VerticalFov`: 73.74 degrees for 90), so wider windows see more at the sides like QuakeSpasm; `gamma` is a screen effect (pow(color, gamma), lower is brighter, off at 1); the bob is Quake's `V_CalcBob` (cl_bobcycle 0.6, cl_bobup 0.5, -7..4 units from the horizontal speed) on the eye, with the weapon forward by 0.4 of it, in the play, QuakeC and demo views. Headless runs keep the defaults and do not save (`VideoSettingsVolatile`), and the demo action `CMD:<console command>` runs any console command. The headless window is 16:9, so the Hor+ field of view widened every reference screenshot (rewritten; the converted-map references are copies of `finish_1` again); unit tests check the vertical angle and the bob's range and period.

**Web Build Persistence and Smoke Test.** `QuakeWebStorage` keeps the engine's in-memory `castle-config:/` across visits: at start `RestoreWebStorage` writes back every `castle-quake:<path>` key of the browser's `localStorage` (base64) before the user config is read, and once a second `SyncWebStorage` stores the files whose content changed (the user config with the bindings, gamepad and video options, the savegames; files above 1 MB such as long demos are left out). The `localStorage` calls live in a small JS helper object with try / catch around everything (private windows, a full quota), since WebAssembly cannot catch exceptions; native builds get no-op stubs. The web build reads `?warp=<map>` and `?autotest=<map>&demo=<actions>` from the page URL (screenshots only log in the browser). The `Web` workflow now runs on branch pushes too and, after compiling, serves the build and runs `tests/websmoke.js` in headless Chromium (Playwright, SwiftShader WebGL): E1M1 starts, renders, saves to a slot whose file reaches `localStorage`, and after a reload the file is restored and the save loads; `tests/websmoke_check.py` checks the two canvas screenshots are not black. Only main deploys to Pages. Saving the options in the browser also showed that the view bob and gamepad dead zone defaults were written to the config (a Single never equals the Double constant); they are compared as Single now.

**Touch Controls.** `GameTouch` draws the editor design `data/ui/touch.castle-user-interface` (scaled with the window height): a move stick on the left that appears where the finger lands, look by dragging on the right half (160 degrees per screen height), and FIRE, JUMP, USE, weapon `<` / `>` and MENU buttons around the corners, clear of the status bar. They feed GameInput's touch state (`TouchMove`, `TouchLookDelta`, `TouchButtons`), which `GamepadMove`, `GamepadTurnCamera`, `BindingHeld` and `UpdateGamepad` / `GamepadJustPressed` add to the game controller's, so the play, QuakeC and network views use them with no code of their own beyond showing them and the menu button. Native builds take each finger from the engine's events (`FingerIndex`); the engine's web backend reports every pointer as finger 0, so a small JS helper tracks the browser's touch pointers by `pointerId` (capture listeners on window) and keeps them from reaching the engine as mouse clicks while the controls are shown. The controls appear by themselves on a touch device or at the first touch in the browser (`-touch` / `-notouch`, `?touch=1` / `?touch=0`), mouse look is off while they are wanted, and the menu now takes taps (an item runs, outside the items goes back; outside the main menu's items resumes the game). The demo script's `TD` / `TM` / `TU` touch down, move and up at window fractions; the `touch` gameplay scenario walks E1M1 with the stick (376 units), turns with a drag (28 degrees), fires with the button and opens the menu with MENU, against a reference of the overlay, and the web smoke test opens a touch page in Chromium (`hasTouch`, touches through the DevTools protocol) where a tap shows the controls and a held drag walks the player about 700 units. Not verified on a real phone.

**Android Package.** `tools/android-fpc.sh <prefix> <ndk>` builds `ppcrossarm` and `ppcrossa64` from the installed FPC's version (3.2.2) and writes an `fpc.cfg` and `env.sh` for `castle-engine package --target=android`. Three things had to be found out: the NDK has no GNU binutils since r23, and `ld.lld` rejects the `INSERT AFTER .data1` of FPC 3.2's Android linker script, so the script uses Ubuntu's `binutils-arm-linux-gnueabi` / `binutils-aarch64-linux-gnu`; GNU ld cannot place the symbol versions (`LIBC_N`) of the NDK's static `libc.a`, so only the API 21 directory with the shared stubs is on the library path; and 32-bit ARM has no `Int64` for loop counters (the `.pk3` reader had one). The `build-android` job of the Build workflow installs Ubuntu's FPC, builds the CGE build tool with it (`setup_castle_engine --install-fpc=false`), caches the cross-compilers, installs SDK platform 36, build tools 36 and NDK 27.3 and packages the APK, which the release attaches: 77 MB (139 MB of data, the paks and music included) with arm64-v8a and armeabi-v7a libraries aligned to 16 KB pages, min SDK 21, target 36. Without a release key the build tool signs it with the debug key, so it installs by side-loading; a store upload (an AAB, `--package-format=android-app-bundle`) needs a release key in `AndroidSigningProperties.txt` from the repository's secrets. Not run on a device or an emulator yet.

**Performance Budgets in CI.** the `budgets` gameplay scenario teleports the player (god mode) to six fixed spots on each of E1M1, E1M3, the LibreQuake hub and lq_e0m2 (the player start and items spread over the level, away from triggers) and logs one second of `Z` frame times with the PVS counts at each. The camera leaf, clusters and shapes drawn are the same on every run; the entities move by about one as monsters walk. `tests/budgets.json` keeps the leaf and the counts of each spot. A run fails when a count grows past its margin (10% + 2 for clusters and shapes, 20% + 3 for entities), when the camera ends in another leaf than budgeted (a moved spot or a change in map loading), when a spot lies outside the map, or when the level changes during the run (a spot on a trigger, which the first choice of hub spots was). `--update` rewrites the budgets with the other references. The frame times are not budgets: they go to `budgets/budgets.json` in the uploaded scenario output and to a table on the workflow run's summary page (`GITHUB_STEP_SUMMARY`). The maps run one after another, so the times are not shared with another process (E1M1 23 to 53 ms per frame under llvmpipe). Lowering one budget, or moving a budgeted leaf, makes the scenario fail with the spot named.

## Phase 10: Community Content

**Server-Side PVS and Delta Updates.** `TQuakeServer.CreateBaselines` keeps each entity's state at the level start and the signon sends it (`svc_spawnbaseline`, `spawnbaseline2` for 16-bit numbers in 666); `WriteEntities` sends the entities whose box touches a leaf of the fat PVS around the client's eye (`TQuakeBsp.FatPvs`, the rows of the leaves within 8 units, and `BoxInPvs`, which the client's own culling now shares), the client's entity always, with only the fields that differ from the baseline. On E1M1 coop a client frame went from about 80 full entities (14 bytes each, over 1100 bytes) to about 7 entities in 61 bytes (258 bytes with all 80 as deltas); the server logs entities sent, outside the PVS and dropped every 10 s, and the deathmatch scenario checks that none are dropped and some are outside the PVS. The client view on E1M1 coop matches the old server's view (one first-frame difference turned out to be a flickering light that the old client shows too). Unit tests check the fat PVS against the leaf's own row and boxes in and outside the map.

**Loose Files and .pk3 Mods.** `TQuakePak.AddDirectory` indexes the directory's loose files (read from disk), `AddPk3` reads a zip's central directory (stored and deflated entries, inflated with paszlib), and `LoadGameDir` loads, per base directory, the loose files first, then the paks (which override them, like Quake) and then the `.pk3`s in name order; a directory reached twice is loaded once, and `GetData` caches unpacked entries. The `gamedir` gameplay scenario builds a mod directory with a loose BSP29 map, a pak0 holding a 2PSB version of another loose map and a deflated `.pk3` holding a BSP2 map and a BSP2 version of a third loose map: all four load, the right container wins each time, and the loose and `.pk3` maps render the reference view.

**Large Coordinates (Protocol 999).** the demo reader (also the network client) reads protocol 999's flags after the protocol number and decodes coordinates as floats, 32-bit sixteenths, 24-bit or 16-bit, and angles as floats, 16 or 8 bits, with all of FitzQuake's extensions. A map whose world model reaches beyond -4096..4095 units (`MapNeedsLargeCoords`) is written as 999 with QuakeSpasm's flags (float coordinates, 16-bit angles) by the demo writer (per level, from `BeginLevel`) and the network server (with the progs' own `WriteCoord` / `WriteAngle` bytes), `-protocol 999` always; other maps stay 15 or 666. With 16-bit coordinates such a map did not wrap but stopped at 4095.875 units. `tests/bsp2convert.py` gained `translate`, which moves a map (vertices, planes, bounds, texture offsets, entity origins) without changing its lighting: E1M1 moved by 8192 units renders the start view like the original (difference 0.1). The `largecoords` scenario records a walk there that plays back at the same place (y 8373 recorded, 8375 played) and runs a coop host and a client beyond 4096 units (the shot reaches the server, prediction error under 3); a unit test round-trips coordinates beyond 4096, 16-bit angles and a sound origin, and shows a protocol 15 level stopping at 4095.875. Scaling a map instead of moving it would also change its hulls, so it is not done. The demo and network views log the view entity's position with each screenshot.

**Fog and Skybox from Demos and Network Games.** `TViewDemo` applies the server's sky and fog: `svc_fog` and a stuffed `fog ...` command (`TQuakeDemoReader.ParseStuffText`, FitzQuake's `fog <density>`, `<r g b>` and `<density r g b> [time]`, which mods send by stuffcmd) go to the engine's fog, `svc_skybox` to `TQuakeGeometry.SetSkybox`, which gives the sky surfaces a new effect at run time (the six faces of `gfx/env/<name>`, or the scrolling sky again) since the map is built before the signon brings the sky. The worldspawn `fog` and `sky` keys are read by `WorldspawnFog` / `WorldspawnSky` (`QuakeBsp`), so the server picks protocol 666 for a level that sets them and sends both in each client's signon, and the demo writer puts the level's sky and fog in its signon (`SetLevelEnvironment`) and records the console's `fog` and the new `sky <name>` command during the level (`WriteFog`, `WriteSkybox`); these FitzQuake messages only go out with protocol 666, so protocol 15 demos stay playable by any Quake. The `envmsg` scenario records a demo on a fogged map, changes its fog and sky from the console and plays it back in a second process (the map's fog, the new fog and the skybox), and runs a host on a map with a sky key (protocol 666) and a client; a unit test checks the round trip and the stuffed fog forms.

**Community Map Regression Set.** `tests/community_maps.py` fetches three Quaddicted maps by URL and SHA-256 into a cache (not bundled: the readmes ask to be asked before redistribution, so "freely available" rather than freely licensed): Temple of Azathoth (`tofaz`, BSP2, 44308 faces, `.lit` and a worldspawn fog), The Isolation (`digs08`, a 38614 face BSP29 with a `.lit`) and The Grim Outpost (`grim`, BSP2). Each loads in its format with its colored light and fog, a play run visits the player start and three items spread over the level away from trigger brushes (spots from the entity lump) where `NC` renders with and without PVS culling and `Z` logs the frame times and PVS counts, and a QuakeC run spawns the level (526 to 599 edicts). It fails on a load error, any pixel that culling changes, PVS counts past the margin of `tests/community_budgets.json` at the same camera leaf, frame times above three times their budget plus 50 ms, or a level change during the run; `--update` rewrites the budgets. All twelve spots render identically with culling on and off. The `community-maps` job of the Build workflow caches the zips and runs it (logs, `community.json` and a summary table as artifacts); it is not a release gate, since it depends on Quaddicted being reachable.

**Captions and Accessibility.** `QuakeCaptions` has captions for about seventy sounds: monsters seeing the player and attacking (soldier to Shub-Niggurath), doors, platforms, buttons, secrets, triggers, teleports, explosions, grenades and rockets, telefrags, every pickup and the powerups. Every sound goes through `TQuakeSounds.Play` / `PlayAt` in the play, QuakeC, demo and network views alike, whose new `OnCaption` hook runs even with the sound turned off. A positional sound gets a hint from the camera (`CaptionDirection` on the horizontal plane, set by `ApplyVideoSettings` each frame): `< left`, `right >`, `^ ahead ^` or `[behind]`, none within 96 units. The HUD design has a `CaptionsPanel` above the status bar with the last four captions for three seconds each, and a repeat (a door's start and stop, a room of soldiers) renews the shown one. High contrast HUD: an opaque black status bar in a yellow frame, white titles and stats, saturated values, and a yellow message and captions. Reduced flashes: the damage and pickup palette shifts at a third, never past 40/255. Options > Captions / High Contrast HUD / Reduced Flashes and the console's `captions`, `hud_contrast` and `reduced_flashes` save them under `access/` in the user config (autotest runs start with them off). A unit test checks the table, the four directions, merging, the limit and the flash scale; the `access` scenario captions E1M1's health box with the high contrast HUD (a reference image), monsters waking in `random42`'s exit room with their direction, and nothing with captions off. The lightning flashes and explosion lights of the 3D view are not reduced.

## Phase 11: New Ways to Play

**Random Map Generator.** `QuakeRandomMap` builds `maps/random<seed>.bsp` (and a `.lit`) the first time anything asks the pak for it (`PakMissingFileHook`, `TQuakePak.AddMemoryFile`), so a warp, `-randommap [seed]`, `?randommap=<seed>` (or `new`), Single Player > Random Map, a changelevel, a demo or a network client all get the same BSP29 file. The layout: 8 to 12 rooms on a 36 x 36 grid of 64 unit columns and 16 unit layers, two cell wide corridors along Prim's spanning tree of the room centers plus one or two loops, floors one step apart (16 units), pillars or a raised dais in some rooms, and the exit pad in the deepest room, which leads to `random<seed + 1>` (an endless chain of levels). The compiler: a k-d tree over the cells (split where the solid count changes between slabs, nearest the middle; each leaf a box of solid or empty cells), the solid / empty boundaries as faces on the node that separates them, merged into rectangles of up to 256 units and with T-junctions fixed, hull 1 and 2 as the same tree over the cells grown by the hull's box, the exit trigger as model 1, lightmaps traced through the cells from the lights (`light - distance` with the angle, like light.exe, colored per room in the `.lit`, a pulsing light style on the exit) and the textures taken from the miptex lump of `start.bsp` by name (walls, floors, ceilings, the exit), or generated when there is none. Entities: the start facing the nearest corridor, coop and deathmatch starts, an intermission camera, monsters picked by the room's place in the order (soldiers and dogs first, ogres, knights, scrags, enforcers and zombies in the middle, fiends, hell knights, vores and shamblers at the end; more in medium and hard via the skill spawnflags), a new weapon (super shotgun to thunderbolt) in each of the first six rooms after the start, ammo for what there is so far, health, armor, ceiling lights and wall torches. A seed is the same bytes on every run (own xorshift generator); a level builds in about 35 ms. A unit test builds five seeds twice (same bytes, different seeds differ), loads them through the pak, checks that every room is reachable on the grid, that the start, monsters and items are in open space for their hulls, and walks the compiled player hull in 32 unit steps (stepping up 18 units, falling) from the start to the exit trigger; the `randommap` scenario walks from the start of `random42`, takes its exit pad to the tallies and `random43`, spawns it with QuakeC and has a network client build the host's `random7` from the name alone. Not done yet: stairs and real height changes, doors, keys and secrets, and a PVS (every leaf sees every leaf, so culling draws the whole level; the levels are small).

**Horde Mode.** `-horde` (with any map, `-randommap` too), `?horde=1`, Single Player > Horde Mode (E1M1 or a random map) and the console's `horde [0|1]` play a map in horde mode (`quakeworld_horde.inc`): the map's monsters are cleared and its exits turned off, and waves of 4 + 2 x wave monsters (up to 10 at once) teleport in at the map's monster, deathmatch and item spots, one of the three nearest ones at least 400 units away that is out of the player's PVS or behind the player. From wave 2 ogres, knights, scrags and enforcers mix in, from wave 5 fiends, death knights and vores, and a shambler closes every fifth wave. Quake's monsters do not find their way around walls, so one that gets no closer for 8 seconds while out of the player's sight teleports in again at a nearer spot (any one 400 units away). Kills score the monster's base health, a cleared wave 100 x wave, and brings the items back after a 5 second pause; the stats line shows `WAVE n   LEFT n   SCORE n` (or the seconds to the next wave). Dying ends the horde (`HORDE OVER` with the score and the map's best, kept in the user config under `horde/<map>/`) and restarts it at wave 1. Saving is off in horde mode, and `killall` kills every monster (a cheat, for tests). The `horde` scenario clears wave 1 on E1M1 with `killall`, checks the score and wave 2, and plays horde mode on `random42`. Not done: coop over the network (the QuakeC games run the progs' own rules).

**Ghost Racing and Speedrun Timer.** `quakeworld_ghost.inc` samples the player's origin and yaw ten times a second during a level (not in horde mode, not after loading a game). Finishing a level (the intermission) faster than the best time writes the run to `castle-config:/ghost_<map>.ghost` (its own small format: the best time and the samples, not a demo; on the web it is kept in localStorage like the savegames), and the log says `Speedrun: <map> in m:ss.cc (best ..., +/-d.dd)`. With the ghost on, the next runs show the best one as the player model, translucent and bluish, running or standing along the recorded path (interpolated, hidden while it is on the player and after its finish). Every five seconds of the ghost's run is a checkpoint: when the player comes within 128 units of it, the time is compared with the moment the ghost first came that near and the stats line shows `GHOST -0.81` for three seconds. The speedrun timer shows `RUN m:ss.cc` there and the split at the end (`NEW RECORD`, or the time behind). Options > Speedrun Timer / Ghost of the Best Run, the console's `speedrun`, `ghost` and `ghost_reset`, and `-speedrun` / `-ghost` on the command line; saved under `speedrun/` (the ghost on, the timer off by default). The `speedrun` scenario keeps a first run of E1M1 as the ghost and races it at half speed: behind at the checkpoint and at the end, and not kept. Splits are per level (and per checkpoint), not across an episode.

**Bots for Deathmatch.** `QuakeBots` (`TQuakeBots`, owned by the listen server). Bots are fake clients of the server's `TQuakeQcGame` rather than network clients: each takes a free client edict (`ConnectClient`, so the progs' `ClientConnect` / `PutClientInServer` and the deathmatch rules apply to them) and every server tick feeds `RunClientInput` with the move, angles, fire and weapon impulse it decided, so they run through the same player physics, `PlayerPreThink` / `PlayerPostThink`, items, damage and respawns as the players, and reach the network clients like any other player (names, frags, the scoreboard). Navigation is built when the level loads: a flood fill of the player hull over the floors from the spawn points and items in 64 unit steps (up stairs of 18 units, down drops of at most 240, kept in a 32 x 32 x 24 cell dictionary), with the links between neighbours (E1M1: 3072 spots, 17117 links in about 35 ms); paths are Dijkstra searches with a binary heap. A bot picks the item worth most for its distance (weapons it lacks, health when hurt, armor, ammo, powerups) and roams to random spots when nothing is worth it; a goal it cannot reach is avoided for 30 s. It fights the nearest visible player within 2500 units (a hull 0 trace) after a reaction time, with an aim error and turn rate set by the skill, strafes, closes in from afar and backs off when too near, and switches to the best weapon with ammo for the range; it jumps when stuck, picks another goal when still stuck after 2 s, swims up in water and fires to respawn. `-bots N` with `-host` (or `--autotest host:<map>`), Multiplayer > Deathmatch vs 3 bots, `-skill` sets their skill. The log says `Navigation of "<map>": ...`, `Bot "<name>" joined as client E` and every 10 s each bot's frags, health, distance travelled and goal. Needed for it: the QuakeC player's think now runs after `PlayerPreThink` (`SV_Physics_Client`'s `SV_RunThink`), so dead players reach their last death frame and respawn, and the nailguns' refire think runs for every client. The `bots` scenario hosts E1M1 with three bots and a network client for 60 s: the bots walk thousands of units each and fight. Not done: bots in the browser alone (the web build has no listen server), team play in coop, and bot chat.

**In-Game Map Browser.** `QuakeMapBrowser` and Main Menu > Map Browser. Quaddicted retired the Quake Injector database (its XML is frozen and says to use the new API, which has no list call yet), so `tools/quaddicted_catalog.py` builds the list from Quaddicted's current metadata (the `quaddicted-data` repository: one JSON per release, keyed by the zip's SHA-256) with the ratings of the last Injector database, and writes `data/quaddicted/maps.txt`: 1202 releases with title, author, date, rating, size, flags (raised limits, BSP2, colored light), start maps, the zip's file mapping and the download URL. Only releases that install into `id1/maps/` and need no mod are listed (mods with their own `progs.dat`, Quoth, Arcane Dimensions, Copper and the like are left out). The menu pages through it ten at a time, sorted by rating, date or name or showing the installed ones; a map's page shows its details and offers Download and play, Play for each start map and Remove. A download (`TCastleDownload`, `CastleHttps`; the manifest's `Https` dependency brings OpenSSL on Windows and Android's `download_urls` service) is checked against the catalog's SHA-256 (`Sha256Hex`, a FIPS 180-2 implementation since FPC 3.2.2 has none) and kept as `castle-config:/quaddicted_<id>.zip`; playing mounts it with `TQuakePak.AddPk3(Url, Mapping)`, which moves the zip's paths by the release's mapping (`MapArchivePath`: `tofaz/` to `id1/maps/`, the longest prefix wins, anything outside id1 is skipped). The console has `maps [rating|newest|name|installed] [text]`, `maps_install`, `maps_play <id> [map]` and `maps_remove`; `-mapcatalog <file or URL>` replaces the list. The `mapbrowser` scenario serves a two-release catalog over HTTP from the test process: a download with a wrong SHA-256 is refused, the good one installs, both its maps (one BSP2) play from the console and through the menu with the virtual gamepad, and Remove deletes it. Checked by hand: Temple of Azathoth downloads from Quaddicted over HTTPS, matches its SHA-256 and plays with its fog and colored light. Not in the browser: the web build lists the maps but cannot keep a zip (its config directory is localStorage). Not done: refreshing the list from the game (run the tool and ship the file), dependencies on other releases, and mod releases.

**Photo Mode.** `GamePhoto` (`TPhotoMode`), shared by the play view and demo playback. P (the new rebindable "Photo mode" binding, the gamepad's View button, console `photo`) stops the game: the world is not updated (the level time stands still), the viewport's items are paused, the HUD, the view weapon and the touch controls hide and a help line from `data/ui/photo.castle-user-interface` shows the keys. The camera flies without collisions with the movement bindings (jump up, walk down), the gamepad's left stick or the touch stick, and looks with the mouse or the right stick. The mouse wheel or `[` `]` change the field of view (10 to 150, horizontal at 4:3 like `fov`), Tab the effect: depth of field (a screen effect reading the depth buffer: the depth at the middle of the screen is in focus and a pixel's disk of 16 samples grows with its distance from that plane over its own distance), grayscale, sepia, vignette or the engine's screen space ambient occlusion; `+` / `-` the photo size (1 to 4 times the window). Enter or the screenshot binding renders the viewport alone off-screen (`TGLRenderToTexture`, `Container.RenderControl` with the viewport resized to the photo, at most 8192 pixels) and saves `<prefix>_photo_N.png` (only logged on the web); R resets, Escape or P leaves and puts the camera back on the player. In demo playback the demo waits while photo mode is on (not in a network game, which cannot wait). Console `photo_fov`, `photo_effect <none|dof|gray|sepia|vignette|ao>`, `photo_scale`, `photo_shot`; demo scripts take them as `CMD:` and `M:` flies the camera in photo mode. The `photo` scenario checks the level time standing still, the camera flying off and coming back, a 3200 x 1800 depth of field photo, a grayscale one at fov 60 (gray pixels) and a photo from `demo1.dem` with the demo time waiting. Not done: a focus distance of one's own (it always focuses the middle), photos larger than the GPU's texture size, and tiles.

## Phase 12: Comfort and Reach

**Save and Load Game Browser.** `QuakeSaveGame.ListSaveGames` / `ReadSaveGameInfo` read `castle-config:/save_<slot>.sav` (QuakeC mode's `qc_save_*` are not listed) and a savegame now records when it was saved (`saved`); `TViewPlay.SaveGameSlot` also writes `save_<slot>.png`, 320 x 180, rendered from the viewport alone (`GamePhoto.RenderViewportImage`, the photo mode's off-screen renderer, so no HUD or menu is in it; not on the web, whose config directory is localStorage). The menu (`smLoad`, `smSave`) shows the selected slot's thumbnail in a frame of the menu design (`SaveThumbnailFrame`, `SaveThumbnail`), Save Game appears only in the play view (`TQuakeMenu.InGame`), the main menu now dispatches by item text, and Load Game from the main menu view starts the play view from the slot (`TViewPlay.LoadSlot`, also `-load <slot>` and `--autotest load:<slot>`). Console `saves` lists them like the menu. Found on the way: the Space key, a click or the gamepad's A that picks a menu item was still held when the menu closed and made the player jump or fire; now jump and fire wait for their release (`FHeldFromMenu`). The `saves` scenario saves slot 8 through the menu with the virtual gamepad, teleports away, loads it back from the newest-first list (the player standing where it saved) and starts a second game with `load:8`; a unit test reads and lists two savegames.

**Controller Glyphs.** `GameInput` tells the family from the controller's name (`PadFamilyOfName`: Xbox and Microsoft first, then Sony, PlayStation, DualShock, DualSense and the DualShock 4's "Wireless Controller", then Nintendo, Switch, Pro Controller and Joy-Con; anything else gets the Xbox names, like the engine, whose own `ButtonCaption` table is chosen at compile time and calls every desktop pad an Xbox one) and names the buttons by position (`PadButtonLabel`: south is A, Cross or B; the bumpers LB / L1 / L, the right trigger RT / R2 / ZR; View, Create or -; Menu, Options or +). The menus confirm with `GamepadConfirmButton` (south, or east on a Nintendo pad where A sits) and go back with the other one. Options > Controls shows the pad's family and has "Gamepad button names" (Auto, Xbox, PlayStation, Nintendo) and "Gamepad confirm button" (Auto, South, East), saved under `gamepad/layout` and `gamepad/confirm`. The prompts use them: the menu's hint line while a pad is connected ("D-pad to navigate, Cross to select, Circle to go back"), the Controls hint (jump, use, fire, photo mode, menu), the map browser's hint (and the D-pad's left / right now turn its pages), the photo mode's help line (a second line with the pad's buttons) and the intermission's "Press fire or A to continue". Found on the way: a pad could not open the menu at all (only the touch MENU button did); now Start / Options / + opens it in a game and closes it, and back on the main page closes it too (`maCloseMenu`). The demo action `PN:<name>` names the virtual pad; the `pads` scenario drives the menu as a DualShock 4, a Switch Pro Controller and an Xbox pad (each confirming into the map browser with its own button, going back and closing the menu without the jump button making the player jump), and a unit test checks the names, labels and confirm buttons. Real pads still need checking (the next item but one above).

**Map Browser Mods.** the catalog now lists 1750 releases: the id1 maps, the mods that install into one directory of their own (Quoth, Arcane Dimensions, Copper...) and the maps whose `dependency=` tag names one of them (maps for the mission packs stay out). Three new columns give a release's game directory, the mods it needs and a mod's own paks inside its zip; a map that installs into `id1/maps/` for a mod lands in the mod's `maps/`. Installing a map downloads the mods it needs first (the menu shows "(N more to come)" and the size with the mods), mounting it mounts them below it with their nested paks (`Pak.AddPakStream`) and sets the game directory, and a mod's map plays in QuakeC mode with the mod's `progs.dat`. The `mapbrowser` scenario serves a test mod with a pak in its zip and a map for it; `tests/community_maps.py` installs Copper with Drowning in Space from Quaddicted and plays it with Copper's QuakeC, and unit tests check the catalog's Quoth entries. A mounted mod stays mounted for the session, and a big one stays in memory (Arcane Dimensions is 320 MB).

**Split-Screen Coop.** `-splitscreen [stacked]` with `-host` (or Multiplayer > Split-Screen Coop) hosts a coop game and joins it twice. The second local client has its own demo reader, camera, HUD and view weapon in a second viewport that shares the first one's world (`Viewport2.Items := Viewport.Items`); the entities and sounds come from the first client, which the listen server sends every entity (`TQuakeServer.SplitScreen`: no PVS culling for clients on 127.x), and each view hides its own player's body and the other player's weapon while it renders (`TSplitViewport.RenderFromViewEverything`). The keyboard and mouse play the first player and the gamepad the second; with two pads the first pad is the first player's too (`GameInput.PlayerController`, a `Player` argument on the gamepad helpers). The HUD now draws its crosshair and intermission inside its own rectangle. The `splitscreen` scenario plays both layouts with the virtual gamepad (the stick walks and turns only the second player, the keyboard script only the first, the trigger fires the second player's weapon, the halves differ), and a unit test checks which player a pad belongs to. Limits at first: the world drew without PVS culling while split, the scrolling sky followed the first player's camera and the browser build had no split-screen (the next item).

**Split-Screen Culling and the Web.** `TQuakeGeometry.UpdateVisibility2` shows the union of the two cameras' PVS rows (the second leaf in the cache key, `SecondLeaf`), and the entities are culled against it again; the scenario's `NC` checks (now also in the network / demo view) find no pixel that culling changes in either view, with 8 to 12 of E1M1's 146 clusters drawn instead of all. Each `TSplitViewport` calls `OnBeforeDraw` before it renders, and the view sends its camera to the sky shaders (`SetSkyEye`). The dynamic lights never depended on the camera (the earlier note was wrong). For the browser, `TQuakeNetSocket` has loopback sockets (`CreateLoopback`): packets go into the queue of the in-process socket on the port they are sent to, as from 127.0.0.1; the web build has no UDP, so its sockets are loopback ones, and a client of a loopback listen server of the page joins it in-process (others still go through the WebSocket relay). `-netloopback` does the same on the desktop, and `?splitscreen=1` (or `stacked`) with `?autotest=host:<map>` or `?host=<map>` hosts split-screen coop in a page. The `splitscreen` scenario checks the culling and plays a loopback run, the web smoke test's fifth visit plays split-screen coop in Chromium (the second player walks, culling changes no pixel), and unit tests send packets between loopback sockets and connect a client to a server over them.

**Localization.** `GameTranslate` reads gettext `.po` files, `data/lang/<code>.po` listed in `data/lang/languages.txt`: German, French, Spanish and Italian, 256 texts each. Texts are translated where they are shown: `Tr` for fixed texts and format strings, `TrItem` for menu items (the whole item, else the label of "Label: value" and a value in brackets, so `Dynamic Shadows: [ON]` and `Field of View: [90]` work while the menu keeps dispatching on its English items), `TranslateDesign` for the labels of the editor designs (the menu's title, the HUD's status bar titles, the touch buttons; it keeps the English texts to translate again after a change). Covered: the menu and its hints, the map browser's items, the HUD's stats line, intermission and messages, the captions (the log stays English), the console help and the `lang` command, the photo mode's help and status, the touch buttons. The language follows the system's (`LANG` / `LC_*`, Windows' user language) until Options > Language (Auto, English, then the translations) or the console's `lang <code|auto>` picks one (`ui/language` in the user config); `-lang <code>` and `?lang=<code>` choose one for a run, and autotest runs are English unless `-lang` says otherwise. `tools/lang_strings.py` collects the texts into `data/lang/castle-quake.pot` (from `Tr` calls, menu items, binding names, captions and design labels) and `--check` (run by the Build workflow) fails when the template is out of date or a `.po` misses a text or changes its format specifiers. Found on the way: long menu pages (Controls, and Options with translations) ran into the hint line; the items now shrink and start higher to fit, and the hint wraps. The `language` scenario plays German from the command line (the menu and map browser hints) and Italian from the console after an English start; unit tests check the `.po` reader, `TrItem` and that every translation covers the template. The engine's default font has no ă, ș or ț, so a Romanian (or a non-Latin) translation needs a font with them first (see Romanian and a Wider Font).

## Phase 13: Further Reach

**Bots in the Browser.** the bots run in the listen server, so with the loopback sockets they needed only a way in: `?bots=N` with `?host=<map>` or `?autotest=host:<map>`, and the menu's Deathmatch vs 3 bots now works in the browser. The web smoke test's sixth visit plays E1M1 against three bots in Chromium (they join, walk over 500 units each and the page's player plays with them), and the `bots` scenario adds a loopback run (`-netloopback`). A deathmatch spawn can be a dark corner, so that visit's screenshot is only checked to show a picture.

**Four-Player Split-Screen.** the further players are `TSplitPlayer`s (2..4), each with its client, demo reader, viewport, camera, HUD and weapon; `-splitplayers N` (`?splitscreen=3` or `4` in the browser) starts with N, and in a game a pad that belongs to no player joins as the next one when its Start is pressed (log `Split-screen: pad N (...) pressed Start: player P`), which re-lays the views: two side by side or one above the other, three with the first on top and two below, four in a 2 x 2 grid. `GameInput.PlayerController` gives player 1 the keyboard and mouse (and the first pad when there is one more pad than gamepad players) and players 2..`SplitPlayerCount` the next pads in order (`PadPlayer` tells a pad's player). Each view hides its own player's body and every other player's weapon, and `TQuakeGeometry.UpdateVisibilityAll` culls to the union of every camera's PVS (the cache keyed on all their leaves). The HUD design fits a quarter of a 1600 x 900 window as it is. The demo script got `PADS:n` (that many virtual pads) and `PAD:i` (the pad `GL`, `GR`, `GT` and `GB` drive); the `splitscreen` scenario plays four players (the second pad walks only player 3, the third turns only player 4, four equal views, no pixel changed by the culling) and a third player joining a two-player game with Start, and a unit test checks which pad belongs to whom with three pads for four and for two players.

**Romanian and a Wider Font.** `code/gamefontui.pas` is a texture font made by `tools/font/make_ui_font.sh` (CGE's `texture-font-to-pascal`) from DejaVu Sans at the default font's size with the 2113 characters of `tools/font/ui_font_chars.txt` (ASCII, Latin-1, Latin Extended-A, the comma-below ș ț Ș Ț, quotes and dashes); it is compiled in, so the browser and Android have it too, and becomes `UIFont` and the container's default font at start. **Mods Without the Memory Cost.** `TQuakePak` keeps every archive on disk that is a file (the bundled paks, `-game` paks and pk3s, the map browser's zips) open as a file stream and reads an entry with a seek when it is asked for, so a mounted mod costs its directory, not its size; only the web build and Android's bundled data, which are no files, still copy an archive into memory. A mod's pak inside its zip is read in place when stored and unpacked once to `castle-config:/quaddicted_<id>_<pak>` when deflated. Each release's archives carry its id as a mount tag: mounting a map unmounts the releases it does not need (its own mods stay), the files they replaced come back, `QuakePak.GameDir` returns to the start's, and the model, sound and brush model caches key a mounted file by its tag, so a model of one mod is never shown in another's map (or id1's). The log says `... read from disk`, `Unpacked "<pak>" to ...`, `Unmounted "<id>": N archives` and `Mounted "<id>" ...; N archives read from disk, K KB in memory`; the console's `maps_mount <id>` only mounts. The `mapbrowser` scenario's mod run mounts a map with its mod, the mod alone (the map unmounts), plays an id1 map (the mod's zip and its two paks unmount) and the mod's map again (the unpacked pak is used again); a unit test writes a zip with stored and deflated files and paks, reads them from disk, unmounts and checks that the base pak's file comes back.

## Phase 18: Faster, Better Looking, Simpler

**One Entity Renderer for the QuakeC and Demo Views.** `GameEntityRenderer` (`TEntityRenderer`, `TEntityVisual`) holds what `gameviewqc.pas` and `gameviewdemo.pas` each had a copy of: showing an Alias model, a sprite, a brush model file or one of the map's brush entities, pose blending, entity alpha, the model trails, `r_lerpmove`, the temp entities' particles, sounds and lights, the lightning beams and the lookup of a mod's `effectinfo.txt` effects. A view keeps its array of visuals and calls `Show`, `Hide`, `ApplyAlpha`, `TempEntity` and `UpdateBeams`; the demo view's `ShowVisual` is a wrapper that turns a protocol entity state (model index, colormap, alpha byte) into that call. A visual is keyed by its model name in both views. The two views lost 870 lines for a unit of 660, items spin in QuakeC mode as they do in demos (`MF_ROTATE`), and the beam segments are freed with the level.

**Mod Effects in Demos and Network Games.** The demo / network view owns the global `EffectParticles` like the QuakeC view: it loads `effectinfo.txt` at its start (before a listen server spawns the level, whose progs ask for effect numbers), updates the particles facing the first view's camera and frees them when it stops, so the shared renderer's `EffectByName` and `EffectTrail` find the mod's TE_ and TR_ effects there. A host's own view also shows what its progs make with `pointparticles`. Screenshots log `Effect particles: ...` as in QuakeC mode; the `fxmod` scenario hosts a game with its test mod and checks the shotgun's impacts come from it.

**Area Grid for Entity Traces.** `TQuakeQcGame` keeps the linked entities in a grid of 256 unit cells over the world's X and Y (at most 64 x 64; a box over more than 36 cells goes into a list every query takes). `LinkEdict`, which the engine calls after every move, `setorigin`, `setmodel` and `setsize`, puts an entity into the cells of its box (`GridLink`); `GridVerify` at the start of a frame relinks what the progs moved or resized by assignment and unlinks the freed. `TraceBox` asks `GridQuery` for the entities whose cells the move's box (72 units wider, for the clip hulls of brush entities) covers and tests them in ascending order, as before, so ties still go to the lower edict; `PlayerTouchTriggers` uses it too. `findradius` still walks every edict, as Quake's does without linking. `UseAreaGrid` turns it off for the unit test, which makes 2000 random traces through E1M1 both ways and gets the same entity and fraction each time. QuakeC-mode screenshots log `Entity traces: N, M entities tested each of E edicts`: 39.9 of 4091 on `ad_sepulcher`; the `quakec` scenario checks the line. Found on the way: the player physics' contents hook of 0.3.64 (`OnContents`, for brush entities that are water) was assigned outside its loop in `TQuakeQcGame.Create`, so players never swam in them; fixed, and the unit test now puts the player into such an entity and checks the water level.

**Batched Engine Particles.** `TQuakeParticle` is now plain data (position, velocity, color, life, scale, alpha) and `TQuakeParticleManager` owns one scene: an `IndexedTriangleSet` with a color and texture coordinate per vertex, rebuilt in `Update` as quads facing the parent viewport's main camera (`TCastleRootTransform.MainCamera`), textured with a soft dot and left alone while there are no particles. The `Spawn...` methods and their callers did not change. Before, every particle was a `TCastleScene` with its own nodes and material, and its quad lay in the XY plane instead of facing the camera.

**Smooth Movement in Demos and Network Games.** The server and the demo writers set `U_NOLERP` for `MOVETYPE_STEP` entities, as Quake's server does (`TNetEntityState.Step`, `TDemoEntityState.Step`); the reader keeps the bit, and the demo view's `ShowVisual` passes it to the shared renderer's `LerpMove`, so a stepping monster glides from where it was drawn to its new place over 0.1 s (id's own demos carry the bit too). Demo and network screenshots log `Entities gliding between steps: N`; the `quakec` scenario records its fight as a demo and checks the monsters glide in the playback.

**Stable Network Scenarios.** `-spawnspot N` (`QuakeServer.ServerSpawnSpot`) makes the listen server move every player that connects (not the bots) to the map's deathmatch spawn spot N, N + 1... in the order they join, after the progs put it somewhere (`TQuakeQcGame.PlaceAtSpawnSpot`, log `Client E placed at spawn spot K of M (x y z)`); the progs' own choice depends on who joined first, so the same scenario started in a different room each run, sometimes an unlit one. The `netrecord` and `bots` scenarios use it and their clients must be lit again. `tests/scenarios.py` plays a scenario with a host or a client once more when a check fails (`is_network`, `play`) and prints `retry after: <check>` for each failed check of the first try.

**Anti-Aliasing and Texture Filtering Options.** `QuakePalette.TextureSmooth` and `TextureAnisotropy` with `SetupTextureFilter` replace the fixed filters of the world's, the models' and the sprites' textures (anisotropy only for the world); they are read when a level's textures are made, so a change shows on the next level. `GameVideo.AntiAliasSamples` is the window's multisampling: `GameInitialize.SavedAntiAliasing` reads `video/fsaa` from the user config before the window opens (desktop only; not for headless runs), so a change shows after a restart, and the engine falls back to none where the display cannot do it. Options > Texture Filter, Anisotropic Filtering and Anti-Aliasing cycle them; the console has `gl_texturemode <nearest|linear>`, `gl_texture_anisotropy <1..16>` and `vid_fsaa <1|2|4|8>` (log `Video: texture filter ..., anisotropy N, anti-aliasing N samples`). The defaults are what the game did before (blocky, 4x, off). The `video` scenario shows E1M1's wall beside the player with blocky and with smooth texels and compares their edges; it turns the anisotropic filter off first, because Mesa's software renderer smooths magnified texels when it is on (some drivers do: set it OFF for hard texels there).
